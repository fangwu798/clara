# Clara 项目面试准备指南

> 目标：不是背代码，而是能用「问题 -> 设计 -> 取舍 -> 故障处理」讲清这个项目。
> 建议先看第 1、2、3 节形成整体框架，再按第 4 节逐题练习。

## 1. 30 秒项目介绍

Clara 是一套面向 Java 8 的 AI 应用运行时库，核心目标是把模型调用、会话记忆、工具调用、MCP、工作流和动态任务规划收敛到一条可复用的对话编排链路中。

项目采用模块化单体结构：`core` 放契约和错误模型，`transport` 统一 HTTP/SSE，`model` 做多平台协议适配，`memory` 管理窗口与语义记忆，`mcp` 接外部工具，`workflow` 执行 DAG 与人工确认，`orchestration` 负责把模型、记忆、技能和工具串起来，`application` 负责装配和 CLI。

我负责/重点参与的部分可以概括为三件事：第一，统一多模型平台调用与故障转移；第二，构建「窗口记忆 + 语义召回 + 工具结果压缩」的上下文治理链路；第三，接入 MCP 与代码知识图谱，让模型优先使用结构化事实，缺失时再读本地文件。

## 2. 一页纸项目地图

### 2.1 模块职责

| 模块 | 职责 | 面试时可讲的重点 |
| --- | --- | --- |
| `clara-core` | 契约、枚举、错误模型、跨模块值对象 | 不依赖业务模块，保证依赖方向稳定 |
| `clara-transport` | HTTP/SSE、超时、体积上限、有界流 | 模型和 MCP 共用一套传输语义 |
| `clara-model` | Provider 配置、协议编解码、流式调用、Token 估算 | 隔离供应商差异，新增平台不改业务代码 |
| `clara-memory` | 窗口记忆、本地/JDBC 会话、语义记忆 | 窗口裁剪、压缩、Milvus 召回 |
| `clara-mcp` | MCP 客户端、注册表、能力快照、工具路由 | 发现与调用分离、能力契约校验 |
| `clara-workflow` | 工作流定义、DAG 执行、预算、人工节点 | 可恢复、可挂起、可人工确认 |
| `clara-skill` | 技能注册、Schema 校验、工具执行 | 本地能力封装 |
| `clara-orchestration` | 对话编排、上下文装配、工具往返 | 只依赖接口，不依赖具体 Provider/Store |
| `clara-application` | 装配、CLI、文档、媒体、图谱运维 | 组合根，负责把能力接起来 |

### 2.2 依赖方向

```text
application
   |
   v
orchestration ---> core contracts
   |                  ^
   +--> model --------+
   +--> memory -------+
   +--> mcp ----------+
   +--> workflow -----+
   +--> skill --------+

transport -> core
model/mcp -> transport
```

一句话：**业务模块不反向依赖 application，orchestration 只通过接口使用能力模块。**

### 2.3 关键设计选择

- Java 8 基线：面向存量企业 Java 系统，方便嵌入。
- 库 + 控制台，而不是开箱即用的 Web 服务：REST/SSE、鉴权、持久化由宿主决定。
- 模块化单体，而不是微服务：当前规模下部署简单，接口边界清晰；未来可按模块拆分。
- 配置化 Provider：通过 YAML 描述平台、端点、凭据、能力和协议差异。

## 3. 一次对话的完整链路

```text
CLI / 宿主
  -> ConversationRequest
  -> DefaultConversationOrchestrator.converse
  -> 写入本轮用户消息
  -> IntentPlanCoordinator.prepare
       - 简单任务：直接回答
       - 复杂任务：生成计划 -> 校验 -> 注入本轮 system
  -> ContextAssembler.assemble
       - 窗口裁剪
       - 工具结果压缩
       - 超限历史摘要
       - 技能匹配
       - 代码知识图谱补充
       - 语义记忆召回
  -> CapabilityDispatcher.invoke
  -> 有工具调用?
       - ToolRoundTripCoordinator
       - CompositeToolInvoker：本地技能优先，MCP 兜底
       - 回填工具结果，继续循环
  -> 无工具调用或达到轮数上限
  -> 返回结果、记录 usage、写会话历史
```

关键点：

- 循环出口是「响应不再包含工具调用」。
- 工具失败通常以错误文本回填，而不是直接中断整轮，让模型有机会修正。
- 执行计划只作用于当前轮，不写入历史。
- 取消令牌贯穿模型读取、工具执行和循环检查点。
- 上下文超限不是直接失败，而是压缩后重试。

## 4. 高概率面试题与回答骨架

### Q1. 为什么拆成这么多模块？会不会过度设计？

回答骨架：

- 这不是微服务拆分，而是**依赖边界拆分**。核心目的是让 `core` 稳定、让 `orchestration` 只依赖接口、让具体 Provider/Store/Transport 可以替换。
- 典型变化点被隔离：新增模型平台只改 `model` 和配置；换向量库只改 `memory`；换 MCP 传输只改 `mcp`。
- 代价是模块和 POM 变多、调试链路变长。当前项目属于平台型基础库，这个代价可以接受。
- 如果只是业务应用，我会合并为更少的模块；如果团队规模继续扩大，再按变化频率拆。

可能的追问：**怎么防止循环依赖？**
答：`core` 不依赖业务模块；`orchestration` 面向接口；`application` 只做装配。Maven 模块依赖和代码评审一起保证方向。

### Q2. 新增一个模型平台需要改哪里？

回答骨架：

- 在 `config/model-providers` 增加 YAML，描述 provider、endpoint、credential、capability 和协议字段。
- 在协议枚举和 `@ProviderAdapter` 元数据中补齐平台差异：字段名、默认值、支持范围、是否丢弃。
- 复用统一的 `CompatibleStream + IHttpExecute` 调用链，不需要在业务层写平台分支。
- 最后用可用性探测和一条最小对话请求验证。

优点：平台差异是数据/注解，不是散落在业务里的 `if/else`。
代价：注解和配置驱动有学习成本，出错时排查链路更长。

### Q3. 为什么意图判定不携带历史？

回答骨架：

- 意图判定的目标是「本轮输入是否需要多步骤执行」，大多数情况下只依赖当前请求。
- 只发送 system 路由提示 + 当前 user 输入，输入 token 固定，不受历史长度影响。
- 计划校验重试只附带上一轮模型的原始 JSON 和错误说明，这是修正所需上下文，不是会话历史。
- 代价是指代型输入可能误判，例如「继续刚才那个」「把第二步改一下」。可以在本地规则中把这类承接型表达直接判为复杂，或后续引入会话摘要；当前优先保证判定成本和边界清晰。

### Q4. 复杂任务的动态计划怎么保证可执行？

回答骨架：

- 模型输出严格 JSON：`mode`、`reason`、`goal`、`steps`。
- `ExecutionPlanValidator` 校验：步骤数、id 唯一、依赖存在、无环。
- 优先调用内置工具 `validate_execution_plan`；工具不可用时退回本地校验。
- 校验失败最多修正一次，仍失败就降级为简单任务，不阻断对话。
- 计划只在本轮作为 system 指令注入，不写入历史，避免污染后续上下文。

追问：**为什么不直接让模型自己按计划执行？**
答：模型可能漏步、重复或跳过验证；显式计划和结构校验能把「思考」和「执行约束」分开。

### Q5. 最近 10 轮强制保留，和 token 上限冲突怎么办？

回答骨架：

- 窗口裁剪按「对话轮次」分组，用户消息开启一轮，后续助手消息和工具往返归入同一轮。
- 最近 `recentTurnsKept` 轮优先于条数/字节/百分比限制，避免最近上下文被工具结果挤掉。
- 系统指令始终保留。
- 真正的兜底是 `ContextOverflowPolicy`：上下文超限时先压缩窗口、缩短工具输出，最多恢复两次；响应体超限时只收紧单次输出上限，不重跑工具。
- 如果 10 轮本身超过平台上限，当前策略会优先保留最近轮次，再由压缩和平台错误恢复兜底；更严格的生产策略可以增加「最大轮次 + 最大 token」双阈值并显式告警。

追问：**为什么按轮次不按消息条数？**
答：一轮可能包含多次工具调用，按消息条数会把一轮拆碎，导致「最近 N 轮」退化成「最近 N 条」。

### Q6. 语义召回为什么只补充窗口外内容？

回答骨架：

- 最近窗口内的消息模型已经能看到，再召回一次会重复占用 token，并让「召回命中」指标失真。
- 召回时把本轮可见消息传给协调器，文本一字不差则静默跳过。
- 为避免最近高相似度消息占满 `topK`，候选数扩展为 `retrievalCount + 可见消息数`，上限 100。
- 阈值由编排层统一判断，存储层不预过滤，便于区分「库里没有」和「有但分数不够」。
- 只报告窗口外候选和过阈值条数，不逐条打印被丢弃内容，日志更干净。

追问：**BM25 和向量检索怎么选？**
答：本项目默认 BM25，因为离线嵌入没有语义、分数过不了阈值；BM25 对中文分词和词命中更稳定。接真实 embedding 后可以切向量模式，但要同时评估召回率、成本和延迟。

### Q7. MCP 是怎么接进来的？

回答骨架：

- 启动期发现：连接 MCP 服务端，执行 initialize 和分页 list，把 tools/resources/prompts 固化成能力快照。
- 调用期不重复发现，只拿快照办事，降低每轮延迟。
- 快照是契约：协议版本、服务端身份、每个能力的 schema hash。
- 调用前做漏斗校验：注册项存在、状态 ACTIVE、快照健康、能力存在、schema 一致，再真正发出调用。
- 传输层支持 stdio 和 Streamable HTTP；协议层和业务路由层解耦。

追问：**快照过期怎么办？**
答：宁可显式失败并提示刷新，也不要拿旧 schema 调用真实服务端，否则会出现难定位的参数错误。

### Q8. 代码知识图谱解决什么问题？

回答骨架：

- 大仓库直接让模型读文件，容易读错、读漏、消耗大量 token。
- 编排前先按提问查图谱，把相关符号、文件大纲作为结构化事实注入 system。
- 图谱未命中或不可用时，模型按约定退回本地文件工具，保证能力可降级。
- 支持 `/graph` 查看状态、`/graph import` 导入当前工作目录；容器按工作目录补只读挂载。
- 关键风险是索引过期和「图谱说了但代码已变」，所以图谱结果只作为线索，最终修改仍要读源码和跑测试。

### Q9. 工作流和动态计划有什么区别？

回答骨架：

- 动态计划是「本轮的执行建议」，上下文级、可失败降级，不持久化。
- 工作流是「可复用的流程定义」，有 DAG、条件、循环、预算、检查点和人工确认节点。
- 工作流可以暂停为 `WAITING_INPUT`，用户确认后按同一 instanceId 续接；动态计划不承担跨轮恢复。
- 简单多步任务用计划，稳定、可复用、需要审计或人工确认的流程用工作流。

### Q10. 模型不可用时怎么平滑切换？

回答骨架：

- 启动期按首字符响应时间探测可用模型，得到可用列表和排序。
- 失败时只对「模型不可用」类错误切换：鉴权、限流、超时、5xx、连接失败等。
- 参数错误、内容安全、用户取消、副作用未知不切换，避免掩盖真实原因或重复副作用。
- 当前模型优先，其后按启动期排序依次尝试。
- 如果本轮已经执行过有副作用的工具，不再换模型重试。

追问：**为什么不在故障时重新探活？**
答：探活本身要发一次真实请求，慢模型会再等十几秒；启动期已有排序，故障时直接沿用。

### Q11. 流式调用、取消和截断怎么处理？

回答骨架：

- 流式事件统一映射为 `TEXT_DELTA`、`REASONING_DELTA`、`TOOL_CALL`、`RESPONSE_COMPLETE`、`ERROR`。
- 取消令牌在模型读取和工具执行的检查点生效，取消后以 CANCELLED 收尾。
- 输出被 `LENGTH` 截断时分两种情况：工具参数不完整则拒绝执行；纯文本则保存已生成部分并安排下一轮续写。
- 响应体过大时收紧单次输出上限，不重跑工具，避免重复副作用。

### Q12. Token 成本和可观测性怎么做？

回答骨架：

- 记录每次模型调用的 input/output/cache/total token，并按平台累计。
- 历史消息可估算整段会话 token；`/usage` 同时展示历史和进程内累计。
- 图片、视频、图谱查询单独统计，避免和对话 token 混在一起。
- 关键阶段有 `[意图]`、`[计划]`、`[校验]`、`[图谱]`、`[向量]`、`[tool]` 等 trace，便于定位慢和空命中。
- 成本控制手段：窗口裁剪、工具结果压缩、召回阈值、候选上限、单次输出上限、失败不重跑工具。

### Q13. 工具调用怎么防止无限循环？

回答骨架：

- 每轮对话有最大工具往返次数。
- 响应无工具调用才结束；达到上限返回明确错误。
- 工具失败通常回填错误文本，让模型修正，但不会无限重试同一个工具。
- 取消令牌和超时贯穿工具执行。
- 有副作用的工具在失败切换模型时不再重试。

### Q14. 这个项目的安全边界在哪里？

回答骨架：

- API Key 从环境变量/配置读取，日志不输出密钥。
- 文件工具限制在工作目录内，防止路径穿越。
- MCP 服务端是外部信任边界，调用前校验身份、协议版本和 schema。
- 命令执行有超时、输出上限和取消检查点。
- 宿主负责鉴权、租户隔离和持久化，库本身不假设自己是公网服务。

### Q15. 为什么不用 Spring Boot / 微服务？

回答骨架：

- 项目定位是「可嵌入的 Java 运行时库」，不是完整产品服务。
- 核心价值在编排和协议适配，不希望强制宿主引入 Web 容器或特定框架。
- 模块化单体降低部署和调试成本；需要 REST/SSE 时由宿主按需封装。
- 如果未来要做多租户 SaaS，再在外面加服务层、鉴权和持久化，不需要重写核心。

### Q16. Sonar 规则和框架约束冲突时怎么办？

回答骨架：

- 先判断规则是否真的指向设计问题，例如构造函数参数过多往往意味着缺少参数对象或 Builder。
- Jackson 的 `@JsonCreator` 这类框架约束可以保留，但要确认规则是否对注解有豁免。
- 本项目删除未使用的 9 参数兼容构造器，保留带 `@JsonCreator` 的完整构造器；测试辅助方法改成接收 `Runnable`，避免规则蔓延。
- 不为过规则破坏公共 API；必要时用 Builder、参数对象或明确的 `NOSONAR` 并写原因。

## 5. 面试官最可能深挖的 10 个点

1. **为什么上下文裁剪按轮次而不是消息数？**
   一轮包含工具往返；按消息数会拆碎轮次，最近上下文不完整。

2. **最近 10 轮硬保留会不会导致请求超限？**
   会，所以需要压缩、输出上限和超限恢复；更严格的生产策略应增加双阈值和告警。

3. **意图判定不带历史，如何处理指代？**
   本地规则识别承接型表达，或后续引入轻量会话摘要；当前优先保证判定成本和边界清晰。

4. **计划生成和意图判定为什么在同一次调用？**
   减少一次模型调用；代价是复杂任务延迟高。若追求更快路由，可拆成轻量路由 + 复杂任务二次规划。

5. **MCP 发现为什么不在每轮做？**
   发现慢且易失败；快照化后调用期稳定，代价是快照过期，需要 schema 校验和刷新。

6. **代码图谱结果可信吗？**
   只作为结构化线索，不作为最终事实；修改前仍读源码、跑测试。索引过期要靠导入/刷新和失败降级处理。

7. **为什么 BM25 而不是向量？**
   离线占位嵌入没有语义，分数过不了阈值；BM25 对中文词命中更稳定。真实 embedding 可用后再切换。

8. **模型切换会不会重复执行工具？**
   已经执行过有副作用工具时不切换；切换只发生在模型不可用且尚无副作用的场景。

9. **volatile 为什么不够？**
   它只保证可见性和有序性，不保证复合操作原子性；需要锁、原子类或不可变快照。

10. **这套架构最大的技术债是什么？**
    模块多、注解驱动学习成本高；MCP/图谱依赖外部进程和容器；内存版注册表和检查点在生产环境需要替换为持久化实现。

## 6. 三个可讲的故障案例（STAR）

### 案例 A：上下文爆限导致任务中断

- Situation：长对话 + 多个工具结果，请求超过平台上下文或响应体积上限。
- Task：不能简单失败，也不能丢掉刚完成的工具结果。
- Action：区分输入侧和输出侧超限；输入侧压缩窗口和工具输出，输出侧收紧单次输出上限；最多恢复两次；压缩只影响本次下发，不改写历史。
- Result：任务可以继续，且不会重跑有副作用的工具。

### 案例 B：模型平台返回 403 / 余额不足

- Situation：某个平台不可用，用户请求失败。
- Task：平滑切换到可用模型，同时避免重复副作用。
- Action：启动期按首字符响应时间排序；失败按错误类别判断是否可切换；当前模型优先，失败后按排序尝试；有工具副作用后不再切换。
- Result：可用性提升，同时保持失败原因和切换行为可观测。

### 案例 C：代码问答读错文件 / 召回为空

- Situation：大仓库中模型直接读文件，容易漏掉引用关系，token 消耗高。
- Task：提高代码定位准确率，同时保留本地文件兜底。
- Action：先查代码知识图谱，把符号和文件大纲注入 system；未命中再走本地文件工具；图谱不可用时自动降级。
- Result：减少无效读取和 token 消耗，代码定位更稳定。

## 7. 白板速记

### 7.1 主链路

```text
Request
  -> Intent
  -> Context Assembly
  -> Model
  -> Tool? -> Skill/MCP -> Model
  -> Final Answer
```

### 7.2 上下文装配

```text
Full history
  -> Window trim (recent N turns)
  -> Tool output compact
  -> Compression summary
  -> Skill prompts
  -> Code graph supplement
  -> Semantic recall (window-external only)
  -> System + messages + tools
```

### 7.3 失败恢复

```text
Model failure
  -> unavailable? -> next model by startup ranking
  -> context overflow? -> compact then retry
  -> output too large? -> lower max tokens then retry
  -> side effect already done? -> stop, do not switch
```

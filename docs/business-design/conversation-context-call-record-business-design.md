# 会话上下文与调用记录 — 业务设计文档

> 状态：已审核
> 阶段：业务文档（本文） → 技术文档 → 实现设计

## 1. 背景与目标

### 现状痛点

**痛点 1：调用过程无留存。** 每次调用大模型的请求内容与响应结果没有被统一记录下来，导致后续无法对历史对话进行总结、复述或理解。

**痛点 2：上下文需客户端手工维护。** 当前每次请求都要客户端自行拼装历史消息，尤其是「模型请求工具 → 客户端执行 → 回填结果 → 再次请求」的工具往返过程，逻辑繁琐且容易出错。

**痛点 3：长对话不可持续。** 上下文没有统一的上限控制，也没有超限后的压缩与向量化回收机制；随着对话变长，既可能超出模型上下文窗口，也无法沉淀可检索的长期记忆。

### 目标

**目标 1：调用留痕。** 每次调用大模型后，在响应结束时记录一条记录（请求、响应、供应商类型、模型类型），供后续对话总结/理解使用。

**目标 2：上下文自动携带。** 由框架自动维护会话历史与工具往返，客户端只需「提问」和「提供工具执行结果」，无需手工拼装历史。

**目标 3：超限可续。** 上下文超限时自动压缩为摘要，并把淘汰的原始消息向量化入库存查，让长对话可持续、可召回。

---

## 2. 术语定义

| 术语 | 定义 |
|---|---|
| 会话（Conversation） | 一次连续的对话，跨多轮请求；有稳定的会话标识 |
| 调用（Call） | 对某个大模型平台发起的一次请求（同步或流式） |
| 历史（History） | 随每次请求一起下发给模型的、按时间排序的历史消息 |
| 工具往返 | 模型返回"需调用工具" → 客户端执行 → 结果回填 → 再次请求的完整过程 |
| 窗口（Window） | 历史允许携带的上限（按条数、具体大小、或百分比） |
| 压缩（Summarize） | 超限后让大模型把被淘汰的历史总结成一条摘要 |
| 向量化（Vectorize） | 把被淘汰的原始消息转成向量存库，供后续按相似度检索 |

## 3. 功能需求

### FR-1 调用记录

每次调用大模型后，在**响应结束**时产生一条调用记录，作为后续「对话总结 / 理解」的原始依据。

**记录内容（仅四项）：** 本次请求内容、本次响应内容、供应商类型、调用模型类型。

**对象一致性：** 记录中的请求对象与本次实际执行调用的请求对象保持一致（同步与流式均如此，不产生第二份）。

**记录时机：** 响应结束之后（同步调用与流式调用各记一条）。

**能力覆盖：** 调用记录覆盖所有能力种类——对话（CHAT）、图片（文生图 / 图生图）、视频、语音。

**可开关：** 未配置记录接收方时，不产生记录、也不影响调用本身。

**消费方：** 调用记录由 clara-orchestration 消费，作为「对话总结 / 理解」的原始依据。

### FR-2 会话上下文自动携带

框架在每次请求前自动把历史消息带入请求，客户端**无需手工拼装历史**。

**历史存放：** memory 负责对话记录的加载、持久化存储与查询；实际使用由 ConvContext 负责——启动 / 继续对话时调用 memory 恢复历史。

**恢复起点：** 恢复历史时若存在压缩记录，以压缩记录作为恢复起点。

**隔离维度：** 历史按「同类型模型」隔离——同一会话内，不同模型（或不同能力）各自持有一份独立历史，互不污染。

**对客户端的要求：** 客户端只负责「发起提问」与「提供工具执行结果」，其余上下文构建全部由框架完成。

### FR-3 工具调用往返自动构建

当模型响应中带有工具调用请求时，框架自动完成「助手请求工具 → 工具结果回填 → 再次请求」的完整往返。

**构建内容：** 模型请求工具时，自动构建一条「助手请求工具」消息，保留调用标识（`callId`）、工具名与参数。

**回填内容：** 客户端执行工具后，框架自动按 `callId` 构建「工具结果」消息，保证与请求一一对应。

**再次请求：** 下一轮请求自动携带完整的工具往返，客户端无需手动维护。

**工具执行：** 具体工具的调用与执行通过 core 定义的接口进行，实现在 `clara-skill`（脚本统一用 Python 执行）。

### FR-4 上下文窗口限制

对可携带的历史设置上限，支持三种维度：**按条数、按具体大小、按百分比**。

**条数限制：** 历史消息的最大条数。

**具体大小限制：** 历史消息的总大小上限（字节数）。

**百分比限制：** 历史所占 token 数占「平台 token 最大值」的百分比上限。

**配置节点：** 窗口限制等上下文控制配置放在 `control` 节点，与模型类型（modelId）同级别——不同类型模型的控制参数可不同；区别于 `parameters`（下发给大模型的调用参数覆盖）。

**默认值：** 默认按百分比 80% 限定、不限制条数；可在配置文件中自行定义覆盖。

**平台 token 最大值：** 配置文件可按平台设置模型上下文窗口的 token 上限，作为「百分比」维度的计算基数。

**组合规则：** 只设一种维度时，该维度单独生效；多种维度同时设置时，**同时满足（AND，取更严）**。

**保留规则：** 系统指令（system）始终保留在首位，不被淘汰。

**淘汰粒度：** 以「完整工具往返」为一组整体淘汰，不会留下残缺的工具调用。

### FR-5 超限压缩

当历史超过窗口限制时，对需要淘汰的部分进行大模型总结，压缩成**一条摘要**。

**触发时机：** 在发送请求之前执行压缩，保证本轮不超限。

**执行方式：** 压缩是一次性独立任务，不走 RAG 递归流程；可采用异步并行执行，注意线程安全。

**压缩模型：** 使用当前上下文中使用的模型进行总结。

**摘要形态：** 摘要作为 system 指令的一部分；产生摘要的这次请求本身不进入历史记录。

**总结提示词：** 总结所用提示词来自 `clara-skill`，通过 core 定义的接口获取。

### FR-6 向量化与检索

被淘汰的原始消息写入向量库，为后续连续对话的知识召回做准备。

**存储实现：** 向量存储采用 Milvus；向量存储与向量检索统一通过 core 定义的接口访问。

**入库：** 被淘汰的原始消息向量化后写入向量库，并关联当前会话。

**检索时机：** 发送请求之前，用当前输入进行检索，检索范围**限定当前会话**。

**检索内容：** 找回当前上下文中没有的相关历史记录信息（被淘汰的消息）。

**注入：** 命中的相关知识作为补充上下文注入，支撑长对话中的知识召回。

### FR-7 流式请求取消

客户端持有流式句柄后，可在流式响应进行中主动取消本次请求。

**取消入口：** 通过流式句柄接口发起取消。

**取消效果：** 请求立即终止，正在进行的读取在下一个检查点停止，本次流以「已取消」的终态收尾。

**安全性：** 取消后仍可查询句柄的完成状态；对已结束或已取消的句柄重复取消不产生副作用。

### 上下文处理设置（control）

处理上下文历史记录时，读取 `control` 节点中的设置信息，各设置项与处理环节对应如下：

| 设置项 | 处理环节 | 说明 |
|---|---|---|
| `contextWindowTokens` | 窗口限制 | 平台上下文窗口 token 上限，作为百分比限制的基数 |
| `windowMaxMessages` | 窗口限制 | 历史最大条数（默认不限制） |
| `windowMaxSizeBytes` | 窗口限制 | 历史最大字节数（可选） |
| `windowMaxTokensPercent` | 窗口限制 | 历史占上下文窗口的最大百分比（默认 80） |
| 压缩开关 | 压缩（FR-5） | 是否启用超限压缩（具体设置项见技术文档） |
| 向量化开关 | 向量化（FR-6） | 是否启用向量化入库（具体设置项见技术文档） |
| 检索条数 | 检索（FR-6） | 每次检索返回的知识条数（具体设置项见技术文档） |

## 4. 业务规则汇总

| 编号 | 规则 |
|---|---|
| R1 | 调用记录发生在"响应结束之后"，同步/流式各记一条 |
| R2 | 记录内容固定为：请求 + 响应 + 供应商类型 + 模型类型（其余不记） |
| R3 | 历史隔离维度：同类型模型（推荐 `供应商+模型`，见 D1） |
| R4 | 窗口限制支持三种维度（条数、具体大小、百分比），可单独或组合设置；组合时取 AND（更严）；默认按百分比 80% 限定、不限制条数 |
| R5 | system 指令永居首位、不被淘汰 |
| R6 | 工具往返（助手 tool_calls + 全部 tool 回执）作为一个整体淘汰 |
| R7 | 超限时：先总结为一条摘要，再向量化被淘汰的原始消息 |
| R8 | 向量检索范围限定当前会话（仅按会话 ID 过滤） |
| R9 | 压缩是一次性独立任务，不走 RAG 递归流程，不引发新的记录 |
| R10 | 流式请求可通过句柄主动取消；取消后以「已取消」终态结束，不再产生后续响应 |
| R12 | 配置文件可设置各平台的模型上下文 token 最大值，作为「百分比」限制的计算基数 |
| R13 | 压缩在发送请求前触发，可采用异步并行执行（注意线程安全） |
| R14 | 摘要作为 system 指令的一部分；产生摘要的请求不进入历史记录 |
| R15 | 压缩使用当前上下文中的模型；向量存储采用 Milvus |
| R16 | `control` 节点与模型类型同级别，不同类型模型的控制参数可不同 |

## 5. 业务场景流程

### 5.1 无工具的单轮对话
```
用户提问 → 框架自动携带历史 → 调大模型 → 响应结束 → 记录一条
        → 框架自动把「助手回复」追加进历史 → 返回用户
```

### 5.2 含工具往返
```
用户提问（"北京天气？"）
  → 框架自动携带历史 → 调模型
  → 响应：模型表示「需要调用 get_weather」→ 响应结束 → 记录一条
  → 框架自动构建「助手请求工具」消息进历史
  → 客户端执行 get_weather → 把结果交给框架
  → 框架自动构建「工具结果」消息（callId 对齐）进历史
  → 客户端再次请求 → 框架自动携带完整往返 → 调模型 → 记录一条
```

### 5.3 超限压缩 + 向量化
```
发送请求前，历史命中窗口上限
  → 取出最旧的连续消息组（整组）
  → 用当前上下文模型异步总结 → 生成 1 条摘要 → 并入 system 指令
  → 被淘汰原始消息 → 向量化 → 写入 Milvus（关联当前会话）
  → 检索（限当前会话）→ 命中知识作为补充上下文注入
```

## 6. 边界与非目标

**不涉及观测日志系统。** 脱敏、截断、SLF4J、日志级别开关等内容本次完全不碰。

**不做向量库本身。** 只做与向量库的对接。

**不做持久化落地实现。** 数据库 / 文件等落地方案只定义「接收方」约定，不做具体实现。

**不改变客户端调用习惯。** 客户端仍以「提问 + 提供工具执行结果」的方式交互。

**多模态能力纳入编排。** 文生图 / 图生图 / 视频 / 语音等能力走统一模型调用入口与调用记录，并在对话编排中作为能力调用纳入编排流程。

## 7. 架构分层约束（已确认）

**core 层：** 只定义结构与契约——窗口规则、窗口执行流程、压缩、向量化所需的接口与数据结构，不落具体实现。「获取总结提示词」「调用工具方法」「执行工具方法」均在 core 定义为接口，直接通过接口调用。

**clara-memory 层：** 负责窗口执行、压缩、向量化等具体实现。

**clara-skill 层：** 负责提供与管理技能——包括总结用的提示词文本，以及执行工具方法（脚本统一使用 Python 执行）。core 定义的提示词接口与工具方法调用/执行接口，由 skill 实现。

**clara-orchestration 层：** 负责把 core / memory / skill 组合成完整对话流程，触发窗口限制、压缩、向量检索注入与工具往返循环。

**control 配置类：** 改造 `ProviderCapabilityConfiguration` 新增 `control` 配置类，承载窗口限制、压缩、向量化等上下文历史处理配置；区别于 `parameters`（下发给大模型的调用参数覆盖）。

**核心接口清单（core 定义，具体设计见技术文档）：**

| 接口 | 职责 | 实现方 |
|---|---|---|
| 总结提示词接口 | 获取压缩总结用的提示词 | clara-skill |
| 工具调用接口 | 调用工具方法 | clara-skill |
| 工具执行接口 | 执行工具方法（Python） | clara-skill |
| 向量存储接口 | 写入向量（Milvus） | clara-memory |
| 向量检索接口 | 按会话检索知识 | clara-memory |
| 调用记录接口 | 接收调用记录 | 宿主 |

## 8. 已确认的业务决策

| 编号 | 决策点 | 结论 |
|---|---|---|
| D1 | 「同类型模型」的隔离维度 | `供应商 + 模型` |
| D2 | 调用记录字段 | 严格 4 项（请求 / 响应 / 供应商 / 模型） |
| D3 | 窗口限制默认值 | 按百分比 80% 限定，不限制条数 |
| D4 | 压缩触发时机 | 发送请求前；可异步并行执行（注意线程安全） |
| D5 | 摘要形态 | 摘要作为 system 的一部分；摘要请求不进入历史 |
| D6 | 历史是否保留 reasoning | 不保留（仅正文），reasoning 只在记录里留 |
| D7 | 压缩模型 / 向量存储 | 压缩用当前上下文模型；向量存储用 Milvus |
| D8 | `control` 位置 | 与模型类型同级别（capabilities.CHAT 级） |

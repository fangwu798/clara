# 后端开发代码规范

> 适用范围：本团队所有后端服务（Java 8 / Spring Boot / Spring Cloud Alibaba / MyBatis Plus）
> 定位：从"模块划分 → 微服务划分 → 表归属 → 引用关系 → 枚举/注解使用时机"五个维度定义后端工程规范
> 适用对象：新服务搭建、新表设计、新功能开发、代码评审

---

## 1. 总则

1. **高内聚、低耦合**：相关的东西放一起（模块/服务/表），不相关的东西不互相引用。
2. **数据主权唯一**：每张表只有一个"拥有者"（微服务），其他服务只能通过接口访问，禁止直连其库。
3. **公共下沉、私有自治**：跨模块共享的东西进 common-core / common-utils；服务内私有东西不进公共包。
4. **声明优于命令**：能用枚举表达的值不写魔法字符串；能由元数据驱动的逻辑不重复手写。
5. **命名即文档**：类/表/字段命名表达归属与语义，配合中文注释。

---

## 2. 业务模块划分

### 2.1 模块划分原则

- 按**业务能力域**划分模块（如：用户、订单、支付、库存、系统配置）；
- 模块之间职责不重叠：同一语义的表、枚举、注解只属于一个模块；
- 模块分为两类：
  - **公共模块 common-core**：不承载具体业务，只放跨模块共享的基础能力；
  - **业务模块**：承载具体业务能力，可被独立部署为微服务。

### 2.2 公共模块内容（每个业务模块的公共部分都收敛于此）

| 类别 | 内容 | 位置 |
|---|---|---|
| 公共实体 | 跨模块共享、被多个业务模块引用的表实体 | `common-core/models/<域>/` |
| 公共 DTO | 跨服务接口出入参 | `common-core/models/<域>/dto/` |
| 公共服务 | 跨模块复用的无状态能力（编号生成、序列化、上下文传递） | `common-core/support/`、`config/` |
| 常用帮助方法 | 通用工具（字符串/金额/集合/时间/脱敏/比较） | **`common-utils`**（统一公共包） |
| 公共枚举 | 跨模块共享的固定取值集合（**仅公共的**放这里，服务内私有枚举留服务内） | `common-core/constant/enums/<域>/` |
| 自定义注解 | 跨模块消费的元数据/标记/行为注解（**仅公共的**放这里，服务内私有注解留服务内） | `common-core/annoation/` |
| 统一基建 | 统一响应 `Res`、业务异常、错误码 `ErrorCode`、公共配置（线程池/序列化） | `common-core/support/`、`config/` |

**放置规则**：

- 一个类**只在一个模块定义**；需要被多个模块引用时，放入 common-core / common-utils，其他模块依赖公共包；
- 业务模块内禁止重复定义 common-core / common-utils 已有的实体/枚举/工具；
- **工具类统一放入 `common-utils` 公共包**（最底层公共依赖：无任何依赖，被所有服务及 **common-core** 依赖）：
  - 服务内**禁止新建 `utils` 目录**；通用帮助方法一律定义在 `common-utils`；
  - `common-utils` 内工具必须是**纯函数/无状态**（不持有业务上下文、不注入 Service），与 `common-core` 的领域能力（枚举、实体）互不混放。

**common-utils 提取范围**（业务类中能提取为公共方法的，尽量提取到 common-utils）：

| 类别 | 示例 |
|---|---|
| 字符串处理 | 判空、拼接、截取、大小写、占位符替换、中英文/拼音转换 |
| 时间/日期处理 | 时间戳转换、日期格式化、相对日期计算、时区转换、月日/年龄计算 |
| 正则 | 手机号/邮箱/证件号/金额校验、正则提取、替换 |
| 金额与数字 | BigDecimal 精确计算、格式化（元/万）、百分比、数值区间 |
| 集合 | 判空、去重、分组、排序、转 Map |
| 脱敏与安全 | 手机号/证件号脱敏、MD5/SHA 摘要、随机 Token 生成 |
| 通用断言 | 非空/相等/范围断言（统一抛业务异常） |
| JSON/序列化 | 对象 ↔ JSON、JSON 数组解析、深拷贝 |

**提取时机**：

- 属于上表**通用能力**的方法：编写业务代码时**直接提取到 `common-utils`**，不必等待被多处复用；
- 属于**业务特定逻辑**（依赖具体业务字段/流程）：就地写在业务类中，禁止上提；
- 评审时发现业务类中存在上表类型的通用方法：**必须**迁移到 `common-utils`。

**common-core 标准包结构**：

```
common-core/
├── auth/                  # 授权：登录态校验、用户/权限上下文、鉴权能力
├── interceptor/           # SpringBoot 拦截器：统一拦截器（reqId 注入、登录态透传、链路追踪）
├── log/                   # 全局日志配置：统一日志格式、MDC 埋点、调用留痕
├── config/                # 全局配置：Feign 配置、JSON 序列化、MyBatis 公共配置、Serializer 序列化/反序列化
├── feign/                 # Feign 接口定义：跨服务调用契约（接口 + 出入参 DTO）
│   └── <域>/IXxxFeignApi
├── annoation/             # 公共自定义注解（仅公共的，见 §6/§7）
├── constant/
│   └── enums/<域>/        # 公共枚举（仅公共的）
├── models/
│   ├── <域>/              # 公共纯模型（仅公共的）
│   │   └── dto/           # 跨服务 DTO
└── support/               # 统一响应 Res、业务异常、错误码 ErrorCode、无状态公共服务
```

- `config/` 内为**全局配置声明**（Feign / JSON / MyBatis 公共插件 / Serializer 等），不触达具体业务表，遵守 3.3 的 common-core 零数据库访问红线；
- **Feign 接口定义统一放在 common-core/feign/**：只定义调用契约（接口 + 出入参 DTO），实现由提供方业务服务完成，契约内不含业务逻辑；
- 各服务只写**业务专属配置**，全局通用配置一律在 common-core/config 定义，禁止服务内重复声明。

### 2.3 业务模块划分（粗粒度）

业务模块按**粗粒度业务域**划分（一般 3~5 个大域即可），避免细到每个子功能一个模块：

| 业务模块（示例） | 职责 |
|---|---|
| 用户/权限域 | 用户、组织、角色、权限 |
| 核心业务域 | 主业务实体与流程 |
| 系统支撑域 | 配置、通知、日志、任务等横向能力 |

规则：

- 同一大域内的相关功能**不拆分模块**，仅在服务内分子包组织；
- 模块最小粒度 = 能独立部署/演进的高内聚业务域，粒度宁粗勿细；
- 具体模块清单随业务演进登记，但必须遵循 2.1 原则。

## 3. 微服务划分

### 3.1 划分原则

- **一个高内聚业务模块 = 一个候选微服务**；
- 独立部署的最小单位是"能独立演进、独立扩容、独立故障隔离"的业务模块；
- 两个模块**强事务耦合**（单事务必须写两模块的表）时应合并为一个服务；反之，互相只读访问的模块应拆分；
- 公共模块（common-core / common-utils）不部署为服务，作为 jar 被各服务依赖。

### 3.2 每个微服务的内部结构（表/脚本/mapper 的自定义脚本位置）

```
<service>/
├── controller/                  # 对外接口（REST / Feign 实现）
├── service/                     # 业务服务层
│   ├── extension/               #   单表基础服务（ITXxxService + impl/TXxxServiceImpl）
│   └── XxxService.java          #   领域编排服务
├── repository/                  # 数据访问层
│   ├── TXxxMapper.java          #   Mapper 接口（extends BaseMapper<Entity>）
│   └── mapper/TXxxMapper.xml    #   ⚠ 自定义 SQL 脚本固定放这里（与 Mapper 同包同名）
├── model/                       # 服务内模型（不跨服务）
├── config/                      # 服务专属配置
├── tasks/                       # 定时任务
└── (utils/)                     # ❌ 服务内不建 utils，通用工具统一放 common-utils
```

**位置强制约定**：

| 产物 | 位置 | 禁止 |
|---|---|---|
| 表定义（DDL） | `_other/patch/v<版本>/dxb_data_<域>.sql` | 不在代码里建表 |
| Mapper 接口 | 服务内 `repository/` | 禁止放到 common-core（表归谁，Mapper 归谁） |
| 自定义 SQL（XML） | 服务内 `repository/mapper/`（与接口同包同名） | 禁止把 SQL 写进 Java 字符串 |
| 实体 | 表归属服务对应模块（跨服务共享才进 common-core） | 服务内自建共享实体 |

### 3.3 模块之间的引用关系

```
                ┌──────────────────────────────────┐
                │  common-utils（最底层，无任何依赖）│
                └──────────────────────────────────┘
                    ▲          ▲          ▲
                    │          │          │  依赖（jar，箭头指向被依赖方）
                    │          │          │
                    │     ┌────┴──────┐
                    │     │common-core│
                    │     └──── ──────┘
                               ▲
                    │          │             
                  服务A      服务B
                    ▲          ▲
                    └── Feign──┘（业务服务间禁止 jar 依赖）
                        调用 
```

> 箭头方向统一为 **指向被依赖方**：服务A/服务B 依赖 common-core、common-utils；common-core 依赖 common-utils；服务间通过 Feign 调用（非 jar 依赖）。

**引用规则**：

| 引用方 → 被引用方 | 允许方式 |
|---|---|
| 业务服务 → common-core / common-utils | Maven 依赖（jar） |
| **common-core → common-utils** | Maven 依赖（jar，**单向**：common-core 可依赖 common-utils，common-utils 禁止反向依赖 common-core） |
| 业务服务 A → 业务服务 B | **禁止 jar 依赖**，只能通过 Feign 接口（定义在 common-core） |
| common-core / common-utils → 任何业务服务 | 禁止（公共包不得反向依赖） |
| 服务 → 其他服务的表 | 禁止直连其数据库，走对方接口 |

**common-core 边界约束（硬性红线）**：

| 约束 | 说明 |
|---|---|
| **禁止访问数据库** | 不引入数据源/连接池/MyBatis 依赖；不含 Mapper、XML、事务；实体仅作纯模型，不做 `@TableName` 持久化映射 |
| **禁止访问其他业务模块** | 不依赖任何业务服务 jar；不调用 Feign / 消息队列 / 远程接口；不读取、不写入任何业务服务的数据 |
| **只允许基础依赖** | 仅依赖 JDK + 基础框架（Spring 核心注解、Jackson 序列化等），保持轻量，保证可被一切服务安全依赖 |

> common-core 只允许存放：公共枚举、自定义注解及纯解析处理器、DTO、无状态模型、基础常量、统一响应/异常/错误码定义。

**落地检查**：新增代码时先问"它属于哪个模块？谁拥有它的数据？"，回答不清就是设计问题。

## 4. 跨模块调用规范

### 4.1 总体调用模型

```
外部客户端/前端 ──▶ gateway（统一网关） ──▶ 业务服务A
                    · 统一认证与登录
                    · 鉴权 / 限流 / 路由 / 灰度
                                         业务服务A ──Feign──▶ 业务服务B
```

- **对外**：所有外部请求一律经 `gateway` 进入；**认证与登录服务统一由网关提供**（登录态校验、token 签发/校验、用户信息透传），业务服务不开放公网、不自建登录逻辑；
- **对内**：微服务之间的调用**默认使用 Feign**（同步 RPC，接口定义在 common-core），特殊强调的场景除外（见 4.4）；
- 所有链路携带 `reqId` 贯穿，全链路可追踪。

### 4.2 对外调用规范（经网关）

| 项 | 规范 |
|---|---|
| 入口 | 全部经 gateway，路径带服务路由前缀（如 `/api/order/**`） |
| 认证 | 登录态由网关统一校验，用户标识、`reqId`、链路头由网关透传给下游服务 |
| 鉴权 | 网关做统一鉴权；资源级权限在服务内校验 |
| 响应 | `Res<T>` 透传，网关不做业务包装，不吞并业务错误码 |

- 业务服务**禁止**对外暴露端口；新接口上线走网关路由配置；
- 登录/认证相关逻辑只存在于网关，服务内取用网关透传的用户上下文。

### 4.3 服务内部调用规范（Feign）

- 服务间调用默认使用 Feign；**接口定义统一放在 common-core `feign/<域>/IXxxFeignApi`**（接口 + 出入参 DTO，禁止定义在业务服务内），提供方服务实现；
- 出入参使用 DTO + 统一 `Res<T>`，禁止直接传数据库实体；
- 超时、重试、降级由 Feign 统一配置管控（全局默认 + 服务级覆盖），不逐方法手写；
- 调用前明确被调服务的归属与边界，禁止越权访问他人数据表。

### 4.4 例外场景（特殊强调的除外）

以下场景允许不使用 Feign，但必须在代码注释与评审中**显式标注原因**：

| 场景 | 允许的替代方式 | 前提条件 |
|---|---|---|
| 异步解耦 / 削峰 | 消息队列（Pulsar/Kafka） | 可容忍延迟，消费端必须幂等 |
| 批量数据同步任务 | JdbcTemplate **只读**目标库 | 专用同步任务、只读、不与业务写混用 |
| 事件通知 | 消息 / 事件 | 单向通知，无需返回值 |

> **跨服务数据一致性默认采用最终一致**（异步消息 + 消费幂等 + 补偿/重试），**不引入分布式强一致事务**（如 Seata `@GlobalTransactional`）；确需强一致的场景先合并服务或重构归属，而不是上分布式事务。
> 未经标注的调用一律按 Feign 处理；绕过 Feign 的调用视为违规，评审一票否决。

### 4.5 红线

1. 禁止业务服务间 jar 依赖（只能 Feign/消息）；
2. 禁止服务直连对方数据库（同步只读例外见 4.4）；
3. 禁止外部绕过网关直接调用业务服务；
4. 禁止在业务服务内自建认证/登录逻辑（统一由网关负责）。

## 5. 表归属规则（每张表归属哪个微服务）

### 5.1 归属判断规则（按优先级）

1. **数据主权**：谁负责"新增/更新/删除"这张表的数据，谁就是拥有者 → 表归属该服务；
2. **事务边界**：与某服务的表在同一业务事务内被写 → 归属该服务（跨服务写默认用最终一致，见 4.4）；
3. **数据访问频率**：被某服务高频读写、字段被其业务模型直接映射 → 归属该服务；
4. **语义聚合**：表属于哪个业务域（如 `t_order_*` 均属订单域）→ 归属对应服务。

### 5.2 归属登记（新增表时必须登记）

| 表（示例，仅示意格式） | 归属服务 | 依据 |
|---|---|---|
| `t_user` | user-service | 数据主权：用户 CRUD 在此服务 |
| `t_order` | order-service | 数据主权 + 语义聚合 |
| `t_order_item` | order-service | 语义聚合（随主表归属） |
| `t_order_log` | order-service | 历史/日志跟随业务表 |

**规则**：

- 每张表在 5.2 中登记且**只归属一个服务**；归属变更需评审并同步更新登记表；
- 配置/字典类表归属"使用它的业务服务"或独立的系统配置服务，禁止散落在多个服务各建一份；
- 历史/日志表跟随其业务表归属同一服务（保证同一事务写入）。

## 6. 枚举定义规范

### 6.1 什么时候需要定义枚举

满足以下**任一**条件，就应该定义枚举：

| 条件 | 例子 |
|---|---|
| 取值集合固定或有限 | 订单状态：待支付/已支付/已取消 |
| 取值有业务语义，需要中文标签/描述展示 | 订单状态：待支付/已支付/已取消 |
| 取值参与代码分支（if/switch） | 订单类型：实物/虚拟 |
| 取值需要跨服务/跨层约定编码 | 业务类型：01/02/03 |
| 取值可能变化但需要一处收口 | 业务状态、来源类型 |

**不需要定义枚举的场景**：

- 一次性自由文本（备注、描述）；
- 纯前端展示、后端不参与判断的文案；
- 值会频繁变化且无固定语义的标记。

### 6.2 枚举放置（可能是公共的，按公共性判定）

**公共性判定**：枚举、注解**可能是公共的**，不强制一律进 common-core；按以下标准判定后放置：

| 判定标准（满足任一 → 公共） | 位置 |
|---|---|
| 参与跨服务 Feign 出入参 / 公共 DTO 字段 | **`common-core/constant/enums/<域>/`** |
| 被 ≥2 个业务服务（模块）引用 | **`common-core/constant/enums/<域>/`** |
| 编码值需跨服务约定传递（状态、类型、业务码） | **`common-core/constant/enums/<域>/`** |
| 仅单个服务内部使用（不跨模块） | 服务内 `enums/` |

- **默认先私有**：新枚举/注解先定义在服务内，出现跨模块引用（Feign 出入参、被其他服务引用）时**上提到 common-core**，禁止复制一份；
- 上提时同步删除服务内定义，保证"同一语义只定义一处"。

**收口规则**：同一语义的枚举只定义一处；服务间传递用枚举编码字符串，接收方用本地枚举映射，禁止跨服务依赖对方枚举类。

### 6.3 枚举命名与结构

```java
@Getter
public enum EnumOrderStatus {
    PENDING("PENDING", "待支付"),
    PAID("PAID", "已支付"),
    CANCELLED("CANCELLED", "已取消");
    private final String code;
    private final String label;
}
```

- 命名 `EnumXxx`，成员名全大写；
- `code`（存储/传输）+ `label`（中文展示）双字段；
- 必须提供按 code 反查的静态方法（`of/getByCode`），禁止 switch 散落。

## 7. 自定义注解定义规范

### 7.1 什么时候需要定义自定义注解

满足以下**任一**条件，才定义自定义注解：

| 条件 | 例子 |
|---|---|
| **元数据驱动**：注解为通用处理逻辑提供声明信息（中文名、分类、忽略规则），消费方是反射/序列化/规则引擎 | `@FieldMeta`、`@TableMeta`、`@IgnoreMeta` |
| **横切标记**：需要 AOP 统一处理的标记（权限、限流、日志、幂等） | `@OperationLog`、`@RateLimit` |
| **声明式替代命令式**：同样的判断逻辑要在多个类重复书写，可收敛为注解 + 处理器 | 校验、脱敏 |

**不建议定义注解的场景**：

- 只有一个消费点、一个类使用 —— 直接写业务逻辑；
- 注解只是"给个名"没有实际处理逻辑 —— 纯装饰性注解禁止；
- 用继承/方法/配置能更清晰表达 —— 不过度使用注解。

### 7.2 注解分类

| 类型 | 特性 | 典型消费方 |
|---|---|---|
| 元数据注解（`@XxxMeta`） | 描述类/字段的语义属性，通常带值（中文名、模板） | 反射解析、序列化器、规则引擎、模板渲染 |
| 标记注解（`@Xxx`） | 无值或仅开关，表示"属于该类/需要处理" | AOP 切点、扫描器 |
| 行为注解（`@Xxx` + 切面） | 触发统一处理逻辑 | `@Aspect` 切面 |

### 7.3 定义规范

- 位置（按公共性判定，见 6.2）：**跨服务消费 → `common-core/annoation/`**；**仅服务内使用 → 服务内**；默认先私有，出现跨模块消费时上提到 common-core；
- 命名：元数据类后缀 `Meta`（`@FieldMeta`），行为/标记类用业务名（`@NeedLog`）；
- 必须显式声明：
  - `@Retention(RUNTIME)`（运行时反射必需）；
  - `@Target`（FIELD/TYPE/METHOD 按消费场景收窄）；
  - `@Documented`（元数据类建议加）；
- **必须配套处理器**：定义注解的同时实现消费逻辑（反射解析工具或 AOP 切面），禁止"只注解无处理"；
- 注解默认值语义清晰，枚举/常量型属性用公共枚举约束取值范围。

## 8. 数据库脚本管理

- DDL 按归属服务拆分文件：`_other/patch/v<版本>/dxb_data_<域>.sql`；
- 结构：`-- Table structure` 建表 + `-- Records` 初始化数据，与表一一对应；
- **可重复执行**（`DROP TABLE IF EXISTS` / `INSERT ... ON DUPLICATE KEY UPDATE`）；
- 每张表、每个字段必填中文 `COMMENT`；实体、Mapper、XML、DDL 四者同步变更；
- 建表类型/索引/主键约定遵循《数据库设计规范》（通用版第 14 章）。

## 9. 开发与评审流程

1. **新增表**：按 §5 判定归属 → 写 DDL → 登记归属表 → 建实体/Mapper/XML/服务；
2. **新增枚举**：按 §6.1 判定 → 决定共享/私有 → 定义 code+label + 反查方法；
3. **新增注解**：按 §7.1 判定 → 定义注解 + 处理器（AOP/反射）成对提交；
4. **新增跨模块调用**：按 §4 检查调用方式（网关/Feign/例外标注），禁止业务服务间 jar 依赖与跨库直连；
5. **评审清单**：归属是否唯一、公共 vs 私有放置是否正确、枚举是否收口、注解是否有处理器、调用是否走网关/Feign、**common-core 是否零数据库/零业务依赖**、DDL 是否可重复执行。
